This package contains the analysis code that produced every figure and table in the manuscript and the supplementary materials. The input data are proprietary and **are not redistributed with this package**; you must obtain access separately (see the [Data](#data) section). The `logs/` and `output/` folders contain the captured Stata output and the generated figure / table files from the authors' run on the proprietary data, so an editor or referee can verify the numbers in the manuscript without needing the data themselves.

## Quick start (one command)

If you already have the data placed correctly and the software installed, the entire replication runs from a single shell command:

```bash
cd replication_package
./run_all.sh
```

This runs the Stata master, the Python post-processing scripts, and writes every figure and table to `output/`. Skip to [Step-by-step instructions](#step-by-step-instructions) for the careful version.

## Step-by-step instructions

### Step 1. Install software

This package has been tested with:

- **Stata 17** or later, with the user-installed packages listed below
- **Python 3.10** or later
- A POSIX shell (`bash`) — used by the driver script `run_all.sh`. macOS and Linux are supported out of the box; on Windows use WSL or Git Bash.

#### Install Stata user packages

Open Stata once and run:

```stata
ssc install reghdfe,    replace
ssc install ftools,     replace
ssc install estout,     replace
ssc install coefplot,   replace
ssc install winsor2,    replace
```

#### Install Python packages

```bash
pip install pandas openpyxl pymupdf
```

### Step 2. Place the data

The cleaned `.dta` files are not shipped in this package; see the [Data](#data) section for the access procedure (data are proprietary and require a data-use agreement with the firm). Once you have the files, place all six of them in a single folder, for example:

```
/somewhere/on/your/machine/data/temp/
├── vacation_connected_call_level.dta
├── vacation_full_data_no_collapse.dta
├── vacation_date_create_time.dta
├── full_data_no_collapse.dta
├── full_data_no_collapse_w_AI.dta
└── full_connected_call_level.dta
```

A handful of additional `.dta` files (`temp.dta`, `temp_A.dta`, `temp_B.dta`, `temp_history_productivity.dta`) will appear in the same folder as the pipeline runs; the scripts create them as intermediate outputs, so you do **not** need to provide them yourself.

The folder names `data/` and `temp/` matter: the Stata code expects to find the `.dta` files at `$data/temp/`. Note the `temp` subfolder.

If you have access to the data through the firm's secure environment but cannot copy it locally, run the package inside that environment and point `$data` at the firm's path.

### Step 3. Configure paths

Open `code/00_declare_path.do` in any text editor. There are two lines you must update before the first run:

```stata
*=== USER-EDITABLE: replication package root =======================
global replication "<REPLICATION_ROOT>"

*=== USER-EDITABLE: location of cleaned .dta files =================
global data        "<DATA_ROOT>"
```

Replace each placeholder with an absolute path on **your** machine, e.g.:

```stata
global replication "/home/alice/replication_package"
global data        "/home/alice/data"
```

Notes:
- `$replication` should point at the folder that contains this `README.md`.
- `$data` should point at the folder that contains the `temp/` subfolder with the `.dta` files. Do **not** include `/temp` in `$data`; the code appends it.
- All other paths (`$temp`, `$figure_overleaf`, `$table_overleaf`, `$replication_log`, `$scratch`) are derived from those two and you should not need to touch them.

### Step 4. Run the package

From the package root:

```bash
./run_all.sh
```

**Expected runtime:** roughly 10–30 minutes on a laptop, dominated by the regressions in `tableA1_summary_statistics.do`, `fig4_case_study.do`, and `tableA6_vacation_or_not.do`, which each ingest the multi-GB full-sample datasets.

**Disk space:** the input data folder is roughly 9 GB. The package itself is a few MB; running it adds ~50 MB of figure / table / log output.

The script does four things:

1. Calls Stata in batch mode to execute `code/00_master.do`, which in turn runs every figure and table do-file in order.
2. Calls `python3 code/tables/table2_revenue_decomposition.py` to produce the final Table 2 LaTeX file.
3. Calls `python3 code/figures/combine_panels.py` to assemble the multi-panel figures (Figures 1–4) with their A/B/C corner labels.
4. Strips identifying paths (e.g. `/Users/<your-name>/...`) from the generated logs so they can be shared without exposing your local filesystem layout.

After it finishes:

| Where | What's there |
|---|---|
| `output/figure/` | One PDF per manuscript figure panel (e.g. `Coef_by_workload.pdf`). |
| `output/figure/Submission/` | The four multi-panel combined PDFs that the manuscript actually `\includegraphics`. |
| `output/table/` | One `.tex` per manuscript table, plus `delta.log` (the calibrated parameter values feeding Table 2). |
| `logs/` | One `.log` per do-file; useful for verification. |

**Auto-detection of Stata.** On macOS the script searches the standard install paths for StataMP, StataSE, then Stata. If yours is somewhere unusual:

```bash
STATA=/path/to/stata PYTHON=python3 ./run_all.sh
```

#### Verifying the run

If the run succeeded, you should see:

- `output/figure/` populated with **14 PDFs** of the panels listed in the [mapping table](#mapping-from-script-to-manuscript-element).
- `output/figure/Submission/` containing exactly **four** combined PDFs:
  `Fig1_outcome_combined.pdf`, `Fig2_workload_combined.pdf`,
  `Fig3_duration_combined.pdf`, `Fig4_case_study_combined.pdf`.
- `output/table/` containing **eight** `.tex` files plus `delta.log`. The eight tables correspond to Tables 1, A.1–A.6, plus `revenue_results_decomposition_table.tex` (Table 2).
- `logs/` containing **18** `.log` files, one per do-file. Each log should be non-empty and should end with `end of do-file` rather than an error.

If any of those is missing or any log ends with an error, see [Troubleshooting](#troubleshooting).

## Data

### Data availability statement

The phone-call records used in this study were collected by a Chinese online medical-insurance brokerage in the course of its normal operations and are proprietary. They contain commercially sensitive information and personal data and **cannot be redistributed**. Researchers wishing to verify the numbers reported in the manuscript can do so by inspecting the captured Stata output in this package's `logs/` folder. Researchers wishing to re-run the analyses on the original data should contact the corresponding author; access requires a data-use agreement with the firm.

### File-level description

The package starts from cleaned `.dta` files. The raw-to-clean step (parsing the firm's Excel exports into Stata format) is **not** part of this package — too many of the cleaning rules are tied to firm-specific conventions to be useful outside the firm.

#### Input files (six)

These are the only files an outside replicator needs to obtain from the partner firm. The pipeline reads all of them; none of them is written to.

| File | Approx. size | Unit of observation | Used by |
|---|---|---|---|
| `vacation_connected_call_level.dta` | 17 MB | One row per *connected* phone call during the holiday and weekend sample. Most regressions in the paper use this. | Figure 1, Figure 2 Panel A, Figure 3, Figures A.3, A.5–A.7, Tables A.2–A.5, Table 2 estimates |
| `vacation_full_data_no_collapse.dta` | 186 MB | One row per call attempt (including unconnected) during the holiday and weekend sample. Used wherever the connection rate or unconditional outcomes are needed. | Table 1, Table A.1 |
| `vacation_date_create_time.dta` | 8 KB | One row per calendar date in the sample with a `vacation_create_time` flag (1 = holiday or weekend). | Table A.6, Figure 4 (joins) |
| `full_data_no_collapse.dta` | 3.8 GB | Same as `vacation_full_data_no_collapse` but covering the full sample (not just holidays/weekends). | Figure 4 Panel B, Table A.6 |
| `full_data_no_collapse_w_AI.dta` | 4.0 GB | `full_data_no_collapse` augmented with an AI-availability indicator at the call level. | Figure 4 Panel A, Figure A.7 |
| `full_connected_call_level.dta` | 439 MB | Connected calls within the full sample. | Table A.6 |

#### Pipeline-created files (not inputs)

These appear in `$data/temp/` once the pipeline runs and are created by the scripts themselves. They are not part of the replication input; documented here only so a replicator who inspects the data folder can recognise them.

| File | Created by | Purpose |
|---|---|---|
| `temp.dta` | `fig4_case_study.do` | Date-level metadata cached for a downstream merge in the same script. |
| `temp_A.dta`, `temp_B.dta` | `fig4_case_study.do` | Small intermediate matrices saved when transferring values across plot blocks. |
| `temp_history_productivity.dta` | `tableA6_vacation_or_not.do` | Per-representative pre-period productivity averages, merged back into the script twice. |

### Variables an outside replicator can expect

Below are the column names that the analysis code references most often. Every dataset listed above contains a subset of these columns; the unit of observation determines which.

| Column | Meaning |
|---|---|
| `if_AI` | 1 if the call was handled by the AI representative, 0 if by a human. |
| `if_connected` | 1 if the call was answered by the customer. |
| `if_succeed` | 1 if the call resulted in at least one insurance transaction. |
| `if_refund` | 1 if any of the resulting transactions was refunded within one month. |
| `bridge_duration_num` | Call duration in seconds (talk time only). |
| `payment_amt_num` | Payment amount on the call (CNY). Per-transaction average for `*_per`. |
| `total_payment_amt_num` | Sum of payment across all transactions on the call. |
| `n_policy_succeed` | Number of transactions completed on the call. |
| `scale_premium_num`, `ins_amt_num` | Scale premium and insurance amount per contract. |
| `gender_customer` | "Female" / "Male" / "Unknown" — customer gender as recorded. |
| `gender_cno` | "Female" / "Male" / "Unknown" — human representative gender. AI is treated as "Unknown" with `if_AI == 1`. |
| `province_capital` | 1 if the customer's province is one of the major (capital-tier) cities. |
| `vacation` | 1 if the call's date is a holiday or weekend in our sample window. |
| `vacation_create_time` | 1 if the lead was *created* on a holiday or weekend. |
| `date_create_time` | Stata date the lead was created. |
| `year_create_time`, `month_create_time`, `day_create_time`, `dow_create_time`, `hour_create_time`, `minute_create_time` | Calendar decomposition of `date_create_time`. |
| `gap_create_first_call` | Seconds between lead creation and the first call attempt. |
| `gap_creat_lastcallthrough` | Seconds between lead creation and the last connected call. |
| `crm_user_id` | Representative-level ID; used as the cluster variable in `reghdfe`. AI is a single ID per system. |
| `working_hours`, `start_working_hour`, `work_month_num` | Human-rep tenure / shift information used in Table A.1 Panel D and Table A.6. |

If your local data uses different column names, edit the relevant `gen` / `keep` / `replace` lines at the top of each affected `.do` file.

## Troubleshooting

**`./run_all.sh: ERROR: Stata binary not found`.**
The driver script tries common macOS Stata install paths. If yours is elsewhere, set `STATA=/path/to/stata` before invoking the script.

**`reghdfe` (or `coefplot`, `esttab`, `winsor2`) not recognized.**
Run the `ssc install` commands listed under [Step 1](#step-1-install-software) inside Stata.

**`file ... not found` on `use "$temp/...".`**
Either `$data` in `code/00_declare_path.do` points at the wrong folder, or the `.dta` file is missing. Verify the path and that the `temp/` subfolder contains all eleven files listed in [Data](#data).

**Logs are empty (0 bytes).**
The master uses `do` (not `run`) so logs should always populate. If you see empty logs, the script almost certainly errored partway through. Open the log of the *first* failing script in `logs/` to see the Stata error message.

**Figures look slightly different from the manuscript.**
Stata graph rendering varies very slightly across versions and across operating systems (anti-aliasing, font subsetting). The numerical content — coefficients, error bars, axis labels — should match the manuscript exactly; the few-percent pixel differences are cosmetic.
